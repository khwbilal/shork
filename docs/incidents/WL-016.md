# WL-016: One analysis came back offline although `claude_code` was selected

- **Work-log item:** [WL-016](../work-log.md)
- **Date:** 2026-10-21
- **Severity:** low (one request; retries worked) · **Status:** open, not reproduced

## Context

End-to-end test of the Claude subscription provider (WL-010). `AI_PROVIDER=claude_code` had been written to `backend/.env` by the startup menu before the server started (uvicorn on port 8767, no `--reload`).

## Symptom

`GET /api/health` returned `"ai_provider":"claude_code"`, and the next `POST /api/analyze` (SOLUSDT 1h, about 11 s) returned `"provider":"offline"` with the offline stub text. No error in the server log.

## Diagnosis

Checked and ruled out:

- The TradingView import does not change `PATH` or `PATHEXT`; `shutil.which("claude")` resolves before and after it.
- In-process, `resolve_provider` returns `claude_code` both before and after a full `fetch_coin_context`.
- `generate_text` dispatches `claude_code` correctly; the offline stub is only reached when `resolve_provider` returns `none`.
- A retry on the same server and later runs on fresh servers all used `claude_code`.

Not explained. One unverified idea: the `.env` file was rewritten several times in that minute (a migration script, then the menu), and pydantic-settings may have read it at a moment it held `AI_PROVIDER=auto`, which skips `claude_code` without a token.

## Fix

None yet. Added diagnostics: the server logs `analyze <pair> <tf> via <provider> -> <bias>` for every analysis, and `resolve_provider` warns `AI_PROVIDER=... is selected but not configured` when a selected provider cannot run.

## Prevention / follow-ups

If it recurs, read the two log lines above for that request. Close WL-016 after a week of normal use without recurrence.
